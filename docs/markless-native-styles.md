# Native styles for Markless components

Markless compiles a `.tsrx` component for the web and, through Dragon, for iOS (UIKit) and Android (Android Views). The CSS in the component's `<style>` block never reaches the device as CSS. At build time Dragon resolves every style of every element, for every state the component can be in, and writes the result as Swift or Kotlin that sets view properties directly. The device runs no CSS parser, no selector matching and no JavaScript; the only Dragon library on the device is the layout engine.

This page describes the one call a Markless build makes, what it must pass in, what comes back, and what happens when the CSS uses something native cannot do yet.

## The entry point

```ts
import { compileNativeStyles } from 'dragon';   // resolved under the `dragon-internal` export condition (node --conditions=dragon-internal)

function compileNativeStyles(config: NativeStylesConfig, input: FrontEndResult): NativeStyles;

type NativeStylesConfig = {
  projectId: string;                       // must equal input.snapshot.projectId
  name: string;                            // the component's name, e.g. 'Chip'; the generated class is DragonChipStates
  targets: { ios?: { minimum: string }; android?: { minSdk: number } };   // at least one
  fonts?: FontMap;                         // the font map (docs/api.md §2.3)
  viewport: { width: number; height: number };   // the CSS size the root starts at, before its view reports its own size
  support?: 'enforced' | 'lanes';          // 'enforced' (default): committed profiles and lanes verdict; 'lanes': as the device lanes compile, never ready
};

type NativeStyles = {
  ok: boolean;                             // true only when every configured target emitted
  digest: string;                          // the compile digest: the same input, config and compiler give the same digest
  diagnostics: readonly Diagnostic[];      // every diagnostic of the compile, each with its source span and target
  targets: { ios?: NativeStyleOutput | NativeStyleBlocked; android?: NativeStyleOutput | NativeStyleBlocked };
};
```

It lives in `packages/dragon/src/native-styles.ts` and is exported from the internal entry only (`src/internal.ts`, which the package's `dragon-internal` export condition selects), not from the public entry. Native emission is experimental under [docs/api.md §1](api.md#1-audience-and-release-boundary), so it has no stable signature yet, and the public entry stays the five names its tests pin. A Markless build that calls it runs Node with `--conditions=dragon-internal`, as `pnpm run native:style-export` does. It compiles with the same settings as `createProject`: the committed support profiles are enforced, and readiness is judged by the committed device lanes record. A bad config (no target, a name that is not an identifier starting with an ASCII capital, a viewport that is not a positive size) throws. Everything about the CSS comes back as data instead.

## What the Markless compiler hands over

`input` is the `FrontEndResult` of [docs/api.md §2.1 and §3](api.md#2-project-input-and-checked-results), built from facts the Markless analyzer already has. Nothing is re-read from disk, and Dragon finds nothing by searching the text.

- **The source snapshot.** Each source's exact text, a stable URI (`dragon-source://<project>/<path>`), a revision and the `sha256:` hash of the UTF-8 text.
- **The style use.** For a `<style>` block, one entry in `tree.styles` whose `css` span covers exactly the block's content: from just after `<style>` to just before `</style>`. Its scope is `{ kind: 'component', owner: '<component id>' }`, so its class names belong to that component only. A global stylesheet uses `{ kind: 'document' }`.
- **The element tree.** Each component's nodes with their origins (source spans): element nodes with their tag, their classes and attributes, and their children in order; text nodes; calls of other components with their arguments; branches for `{cond ? a : b}` markup. A class or attribute that depends on state is a `Choice` over conditions, for example `class={selected ? 'chip selected' : 'chip'}` becomes the class `chip` always and `selected` when `selected == true`.
- **The states.** Each `state()` of the component with its domain (`[false, true]` for a boolean) and its initial value. Dragon compiles every reachable combination, at most 64 per component.
- **A document.** A detached component is compiled inside a small document (`html` > `body` > the component), the same document the Chrome reference renders. The document's global sheet (for example `body { margin: 0; }`) is a document-scoped style use.
- **Completeness.** `'closed-application'`, with the analyzer's own recovered errors in `diagnostics`. A producer error blocks every output.

The ladder fixtures under `packages/parity/fixtures/ms-*/` show the whole shape: each is a real `.tsrx` component (`App.tsrx`) and a `fixture.json` that plays the Markless analyzer. The fixture reader (`packages/parity/src/tree-fixture.ts`) takes a sheet from the n-th `<style>` block of a source (`"block": 0`).

## What comes back for each platform

```ts
type NativeStyleOutput = {
  kind: 'emitted';
  backend: 'uikit' | 'android-views';
  program: StateProgram;                   // the data
  files: readonly GeneratedFile[];         // the code written from that data
  readiness: ArtifactState;                // 'ready' only when every device lane of the target passes
};
type NativeStyleBlocked = { kind: 'blocked'; reason: string };
```

**`program`** is plain data: one node record per element and text run, holding every property write in the platform's own vocabulary (background colour, border styles and colours, corner radii, clipping, paint order, text runs with font and colour, synthetic bold). It also holds the engine input the layout engine lays out. The initial state is stored in full; every other reachable state is a delta of the records it changes. The device lanes judge exactly this program. The test `packages/parity/test/markless-native-styles.test.ts` checks that the entry point's program equals the lanes' program for the same fixture.

**`files`** is one generated source per platform, written from `program` and nothing else:

| Platform | File | Public API |
|---|---|---|
| iOS | `Cases/Dragon<Name>States.swift` | `public final class Dragon<Name>States`, holding a `machine` (a `DragonStateMachine`) and one setter per state |
| Android | `kotlin/dev/dragon/cases/Dragon<Name>States.kt` (package `dev.dragon.cases`) | `class Dragon<Name>States`, holding the same `machine` and setters |

A boolean state gets a `Bool` setter, for example `set_doc_app_chip_selected(_ v: Bool)` in Swift and `set_doc_app_chip_selected(v: Boolean)` in Kotlin. Any other domain gets an enum. Calling a setter swaps in the new state's records and lays out again only when the layout changes. The compiler never runs again, and nothing is matched on the device. The generated file needs Dragon's support files and the translated layout engine in the app. They are the same for every component: `emitNativeSupport(backend)`, and `packages/layout/generated/`.

**`readiness`** is the target's output state from the compile. It is `ready` only when the committed device lanes record (`packages/parity/out/lanes.json`) shows every lane of that target passing and none stale. Until then it is `analysis-only`, and its `reason` names the lanes that do not pass. The code is emitted either way so the lanes and integrations can run it, but only `ready` is a shipping output ([docs/api.md §2.2](api.md#22-no-publishable-partial-output)).

## The export: `dragon.native-style-export/1` (format change from `/0`)

The Markless hosts (`packages/mobile` in Markless) apply styles from a JSON export, not from the generated Swift or Kotlin above. `/0` came from the counter (`examples/markless-counter/tools/export.ts` on the dragon branch `cw/native-targets`). `/1` is the general form, built from `compileNativeStyles`'s output by `nativeStyleExport` (`packages/parity/src/native-style-export.ts`). `pnpm run native:style-export [-- <fixture>...]` writes it for the ladder to `examples/markless-styles/out/<fixture>.native-style.json`.

**What changed from `/0`, for the iOS and Android host workers:**

- `targets.<t>.nodes` is gone. Each target now has `assignments`, one per reachable state combination, and each holds its own `nodes`. Every assignment is complete: no host needs to merge deltas. A component without state has exactly one assignment, whose `nodes` are what `/0` had.
- Each target gains `states` (`[{ key: "<instance>#<state>", domain }]`, in setter order), `initial` (the index of the starting assignment) and `next` (`next[a][s][v]`, the assignment reached from `a` by setting state `s` to its `v`-th domain value, or `-1` when that is unreachable). An assignment's `values` maps each state key to its value.
- Each target gains `readiness`: `{ "kind": "ready" }` only when every committed device lane of the target passes, else `{ "kind": "analysis-only", "reason": "..." }` naming the lanes that do not pass. A host must not ship an `analysis-only` export as proven.
- New top-level field `component`. `compiler` (the compile digest), `units`, `source`, `warnings` and `fonts` are as in `/0`. Ahem is listed as `{ "id": "Ahem", "file": "vendor/fonts/Ahem.ttf" }`; other faces by their `sha256:` id, as before.
- The node shape is unchanged: `id`, `parent`, `kind`, `native`, `text`, `frame` (device px, relative to the parent box), `borderWidths` (device px) and `writes` (each with its `kind` and `key`, as in `/0`). The writes are exactly the state program's, so the hosts and the device lanes see the same data.

**Scrolling (added for the Markless scroll rungs):**

- Each assignment gains `pageScroll`: the viewport's scroll offset range `{ minX, maxX, minY, maxY }` in whole device px, in CSS scroll-offset terms (0 is the start position; the user scrolls between min and max). It is the page's own scroll view: a page taller than the target's viewport has `maxY` above 0. It is `null` when the overflow port does not decide it (a range control, or a form control that is itself a scroll container; a block `<button>` is decided as the plain box it lays out as, checked against Chrome by the `overflow-controls` fixture), and the assignment then carries `pageScrollUndecided: { nodeId, detail }` (the node the engine stopped at, so a framework can name the element in a build error), and the export's `warnings` carry `DRAGON_PAGE_SCROLL_UNDECIDED` with the reason per target.
- A node with a `scroll-container` write (`overflow-x` or `overflow-y` `auto` or `scroll`; `{ kind, key: 'dragonScroll.range', x, y }`) gains `scrollRange`, the same shape, from the engine's `scrollRanges`. Its children's frames stay relative to its border box at scroll offset 0. Other nodes have no `scrollRange` field. A scroll container whose range the engine does not decide fails the command, naming it.
- `markless:style-export` compiles with `output: 'program'`: the state program only, without the generated Swift or Kotlin. The Markless hosts apply the program as data, so a write that only the generated state runtime cannot rebuild yet (a scroll container in a state program) no longer blocks the export. `compileNativeStyles` without `output` still generates the sources and still blocks those targets.

**Text lines (added so Android draws Dragon's glyphs instead of reshaping):**

- A `text` node with a `frame` gains `lines`, one entry per line the engine breaks it into: `{ top, baseline, runs }`. `top` is the line box's snapped top and `baseline` its baseline, in device px from the node's frame (its unsnapped top-left). Each run is `{ face, size, glyphs, xs }`: consecutive glyphs in one face (the `sha256:` id the `font` write names, or `Ahem`) at one instance size in device px (Blink's truncated platform size, e.g. 15px at 2.625 is 39.37, not 39.375), the HarfBuzz glyph ids, and each glyph's pen x in device px from the frame's left. A line holds one run, more with small caps (one per size), plus a run for a truncated line's ellipsis in its own font. A node without a frame has no `lines`; elements never do.
- The data is what Dragon's own native text views draw (`DragonLineSpec` in `emit/native-support.ts`): the engine's breaks (`engineTextLines`), each piece's glyphs from `pieceGlyphs` over the whole shaped item at the line's left plus any justification shift. Draw the glyphs at these positions; do not lay the text out again. Android's Minikin shapes word by word at spaces, so a run like "Basil, in stock" in Inter Bold loses the comma's contextual advance and comes out 1.21 px wider than its frame, and a TextView then wraps it. The node's `text` stays the accessible text.

**How a host switches state:** look up `next[current][s][v]`, then apply the new assignment's frames and writes to the retained views. Nothing is recompiled or matched on the device.

**Chrome comparison of the export:** `native:style-export` also compares every frame of every assignment with Chrome's boxes. It does this at each proof device's viewport and ratio (`EXPORT_DEVICES`: iPhone 17, 402 by 778 points at 3x; Pixel 7, 411 by 818 dp at 2.625), under the device lanes' 1 device px gate. It writes `<fixture>.chrome-compare.json` and fails on any box outside the gate.

The frames are computed at build time for one proof device size. A host on another screen size needs the on-device layout engine, which the generated Swift and Kotlin carry and the export does not. That is the reason both outputs exist.

## From a Markless style input: one command

The proof harness calls Dragon from a sibling checkout with the style input the Markless compiler writes (`markless.native-style-input/0`, from `nativeStyleInput` in Markless's `packages/mobile/src/style-input.ts`) as its only input:

```sh
pnpm --silent --dir "${DRAGON_DIR:-$HOME/wt/dragon/native-dragon-styles}" run markless:style-export -- native-style-input.json native-style.json
```

Relative paths are the caller's. It exits 0 and writes `dragon.native-style-export/1` (above). Otherwise it exits 1 with every reason on stderr: the input is malformed, the CSS does not compile (each error with its code, target and message), or a node of the input is missing from the export. Usage errors exit 2. Markless needs no package dependency on Dragon for this.

What it does with the input (`packages/parity/src/markless-style-input.ts`):

- **Validation.** It checks every field it reads and refuses any field it does not read. It refuses a node inside an `@if` arm or `@for` row (`arm`, `row`), a state whose domain is neither `[false, true]` nor a list of distinct strings (or whose initial value is outside it), a `classByState` that names an unknown cell or does not have exactly one entry per combination of the states, a `classByState` beside a fixed `class`, a node with the id `html` or `body` (the export's own document nodes), and a parent that is not an earlier element.
- **The document.** It builds the element tree under `html` > `body`, with the document sheet `body { margin: 0; font-family: sans-serif; }` and the input's `css` as one document-scoped sheet, since Markless has already scoped it with its `mk-` class.
- **Classes and attributes.** A class attribute is split into its tokens, as HTML does. A `classByState` token present in only some combinations becomes a condition on the states, so Dragon compiles one state program, not one tree per combination. Other attributes are passed as written. A `style` attribute (`base.visuallyhidden`'s) cascades as element-attached author declarations, above every selector at the same importance (css-style-attr §4, css-cascade-5 §6.2); a declaration in it Dragon reads only from stylesheet rules (transitions, animations, `direction`, `unicode-bidi`) is refused by name at the attribute. Checks: `packages/parity/test/markless-style-attribute.test.ts` (the u18 rung's input against Chrome) and the parity fixtures `attr-style-cascade` and `attr-style-visually-hidden`.
- **Ids.** Every export node that comes from the input carries the input's id. Markless names a component's nodes by their path (`component-edge:0/h0`), which Dragon's tree refuses (no `/` or `:`); such an element, and every text node, gets an id `m<k>` no input node uses inside the compile (`dragonNodeIds`). Dragon addresses a text node by its element, `<element>:text<k>`, and a whitespace-only one `<element>:space<k>`, each counted separately (`textAddresser`, exported by Dragon); the export maps each address back to the input text node at that place, counting a text that follows state by the string it shows in that assignment. The command fails if two export nodes share an id, or if an input node is missing from the export, except a boxless element, a node its `hidden` attribute hides in that assignment (named with no frame; on a boxless element `hidden` hides nothing, since its `display: contents !important` wins, as in Chrome), and whitespace-only text, which Dragon drops where it collapses away. A dialog's `::backdrop` box is `<input id>::backdrop`.
- **Attributes that follow state.** `attributesByState: { "<name>": [{ when, value | null }] }` on an element, one entry per combination of the states as `classByState` has: each distinct value becomes a `Choice` over the states (null: absent). Markless sends its `ui-*` attributes this way, so `.status[ui-active]` follows its cell.
- **Text that follows state.** A text node may carry `textByState: [{ when, value }]`, one string per combination of the states (Markless sends it for a text that reads only states). It becomes one branch arm per distinct string, so each assignment lays out, and the export names, the string shown there; before this a longer string was drawn in the frame of the first one. Checks: `markless-string-states.test.ts`.
- **States.** `states[].key` and each assignment's `values` use the input's cells (`state:liked`). A state is true/false or one of a list of strings, the values Markless's compiler found the cell can hold (the selected value of `@markless/ui` tabs: `["a", "b", "c"]`); each value is one assignment and `next[a][s][v]` indexes the list. A `when` names each state's value, a string for a string state. Checks: `packages/parity/test/markless-string-states.test.ts`, every frame of every assignment against Chrome.
- **The canvas and body's box.** Each assignment also has `canvas`, the colour Chrome paints behind the page (css-backgrounds-3 §2.11.2): `html`'s background, else `body`'s, else the base, read from that assignment's own `html` and `body` writes, so a dark band gives its own colour. The base is Chrome's `Canvas` colour in the root's used colour scheme (`colorScheme`, below): white, or rgb(18, 18, 18) when it is dark. A translucent background is given as Chrome shows it: Chrome blends the root background into the base as one colour, each channel (base × (255 − alpha) + colour × alpha) / 255 rounded to nearest, which differs from Skia's src-over by one level on the dark base. In a dark-mode band, a page whose used scheme is light keeps the white base: Chrome 145 (dark preference emulated, as the comparison does) draws even that page over rgb(18, 18, 18), so a see-through page background there is refused by name. And `bodyBackground`: when `html` has its own background, `body` keeps its own for its box (its frame), given composited over the canvas as Chrome shows it (Skia's src-over, `textDecoration.blendOver`); null otherwise (`body`'s background then is the canvas, and its box paints none). The hosts paint the canvas behind the page and under the system bars, and `bodyBackground` at `body`'s frame. A border or any write other than a background colour on `html` or `body` is refused by name, since the hosts draw no other root paint. The Chrome comparison checks every assignment's `canvas`, `bodyBackground` and `colorScheme` against Chrome's, exactly: Chrome's computed background colours of `html` and `body` and the root's used scheme are read from the page, and Chrome paints those colours in a page with no author CSS and no other box, so no pseudo-element, descendant or `!important` rule covers the canvas pixel or the pixel in `body`'s box (read only where `body`'s box shows in the viewport); the root's used scheme (the scheme whose `Canvas` colour the root gives); a difference fails that assignment's row. Checks: `packages/parity/test/markless-root-paint.test.ts`, each colour against the pixel in Chrome's screenshot; `packages/parity/test/markless-style-compare.test.ts`.
- **The colour scheme (`colorScheme`).** It calls `compileNativeStyles` with `canvas: 'host'` (`InternalOptions.hostCanvas`): the hosts paint the canvas, so a page may opt into dark as on the web. Each assignment's `colorScheme` is the root's used scheme there (css-color-adjust-1 §2.1): `light` for no `color-scheme`, `normal`, `light` or `light only`; `dark` for `dark` or `dark only`; and the band's preference for `light dark`, for which the compile adds a `(prefers-color-scheme: dark)` band when no `@media` rule reads the preference. Where it is dark, the page is resolved with Chrome's dark UA capture (`chrome-145.<platform>.dark.generated.ts`), so the writes already carry Chrome's dark default text colour (white), link colour (rgb(158, 158, 255)) and button text colour (ButtonText, white), and `canvas` is drawn over rgb(18, 18, 18). Still refused by name: a box whose used scheme differs from the root's where the scheme recolours it, a form control other than an enabled `<button>`, an auto outline, a root scheme that follows the preference when no band can fix it, and every dark scheme on the web target. **Recorded divergence from Chrome (owner ruling):** a page that does not opt in stays white in a dark-mode band, where Chrome 145 paints rgb(18, 18, 18). Checks: `packages/parity/test/markless-color-scheme.test.ts` (canvas pixel, computed colours and every frame against Chrome in both preferences, for `light dark` and `dark` on the root and for `examples/markless-styles/input/scheme.native-style-input.json`; the divergence by name), `packages/dragon/test/color-scheme.test.ts`.
- **Boxless elements.** `boxless: true` on an element keeps it in the tree for selectors and inheritance and out of the layout: it carries `data-markless-boxless`, and the document sheet gives that attribute `display: contents !important`, as a top-layer `<dialog>` keeps its ancestors. Markless sends a system sheet's markup ancestors this way. Such an element has no node in the export; one whose own CSS still gives it a box is refused by name. The Chrome comparison renders the same attribute and rule. Checks: `packages/parity/test/markless-style-boxless.test.ts`, against Chrome.
- **Viewports.** An input laid out somewhere other than the page names its size per target: `viewports: { ios: { width, height }, android: { width, height } }` in CSS px. Markless sends one input per resting height of a system sheet (`<native.sheet>`), sized to the sheet's content area as measured on the device. Both targets must be named, each in positive whole CSS px (Chrome, the reference, lays out no other size); the export's `viewport` is that size and `dpr` stays the device's. The Chrome comparison (`markless:style-compare`) lays the document out at the export's viewport, so it compares a sheet's content at the sheet's size; it and the web column (`markless:style-web-column`) refuse a target whose `viewport` or `dpr` is not what the input asks for (the export devices' when it names no `viewports`; exactly the phone's size when the web column was asked for an export laid out there, `markless:any-size`), since a browser lays out at whatever size the export states. Both also refuse an export of another component, and a target whose `initial` or `next` is not the state machine the input compiles to. Checks: `packages/parity/test/markless-style-viewports.test.ts`, `packages/parity/test/markless-style-compare.test.ts`.
- **See-through groups and transforms.** A box with a fractional opacity that Dragon pre-composites carries an `opacity-group` write (`opacity`, `backdrop`: the sticky or fixed box whose opaque background must hold it, or null; `painters`: the earlier groups in its backdrop; `after`: the sticky box it paints after, when there is one; `unstable`: earlier painters whose platform rendering may differ from Chrome's, which the device checks stay clear of the group's extent, descendants included). A group with a colour-matrix filter carries a `filter-group` write instead, with the same fields and its `filter` list; the host composites it with `groupFilterComposite`. Its own 2D transform carries a `transform` write (`ops`, `origin`). A host draws the transform as Dragon's `dragonApplyTransform` does (`paint-transform.ts` at the box size, about the box). It draws the group as Dragon's `DragonGroupView` does: an overlay, the group view's last child, shows the group's layer (the platform's rendering of the group's view) composited over the platform's rendering of the root with the group and every view drawn after it hidden, per pixel with `paint-group.ts` `groupComposite`, or `groupCompositeLayered` when `after` is set and the root scroller has a scroll range (`DragonTree.rootScrolls`: a box or line no clipping box below body holds and no fixed box carries reaches past the viewport's end edges, or its start edge in rtl, in pixel-snapped device px); clear where the layer is clear. The hosts model no per-tile fold, so the export refuses by name a group whose own box, or a box inside it, is one draw op (a lone fill, a lone border, a member's outline ring), which cc may fold. Checks: `packages/parity/test/markless-host-groups.test.ts`; Chrome parity of the composite: `packages/parity/test/pnt1-effects.test.ts`.
- **Dashed and dotted borders.** A box with a visible dashed or dotted side also has `borderOps: { origin, size, widths, ops }`: the drawing operations Dragon's own native paint runs for that border (`packages/layout/src/paint-dash.ts`, a port of Blink 145's side painter: fills, dots, clips and opacity layers in device px), with the box snapped to device pixels as Dragon's native views are. `origin` is the snapped border box's top-left relative to the node's frame, `size` that box and `widths` its sides in whole device px. A host draws the operations in order and draws nothing else for that border. A rounded box with such a side is refused by the compile (PNT1b). Checks: `packages/parity/test/markless-dashed-borders.test.ts`, every crisp border pixel against Chrome's at both proof devices.
- **Outlines and paint layers.** An `outline` write carries `layer`, the id of the node whose paint layer paints the outline: the outlined node itself when it is positioned or has a z-index, else its nearest such ancestor, else the root. A host draws the outline in that node's view, after the view's flow children and before its positioned children, each box's descendants' outlines before its own, as Chrome 145 paints a layer (`PaintLayerPainter::PaintLayerContents`). So an outline under a sticky or fixed header is covered by it, and one inside the header moves with it. An outline inside an opacity, transform or other effect layer is refused by name. Checks: `packages/parity/test/pnt1-effects.test.ts` (outline-layers against Chrome) and `packages/dragon/test/paint-outline.test.ts`.
- **Font mode (`fontMode`).** The export says how it resolved fonts, `system` or `pinned`; the Chrome comparison and the web column read it from there.
- **Style values that follow state (typed slots).** An input may list `slots: [{ id, initial, integer? }]`, the numbers the app computes while it runs (a slider thumb's offset, a panel's share), and give an element `styleTemplate: ["--x: ", { "slot": "slot:x" }, "%"]` instead of a fixed `style`. Each hole is written as JavaScript writes the number (`String(n)`), so the CSS around it decides its type as on the web: a number, a percentage (`%` after it), a length (`px`), or an `rgb()` channel. The export is laid out at the initial values. Then, one slot at a time, the command compiles the input at sample values below zero and from zero up (`SLOT_SAMPLES`), and finds every engine-input style field of a box and every number inside a write that the slot moves. Each piece must follow one rule exactly at every sample: `c + k·s`, rounded to a 32-bit float or not (`line`, `line32`), or Chrome's 8-bit channel (`channel`, css/color.ts round8). It records these per assignment in the plan as `slotFields` (Dragon's box id, the style field, and per piece its value and the numbers in it), `slotWrites` (the input's node id, the write's kind, the path to the number, and the rule per piece) and `slotRefusals`. The export and the plan gain `slots`, in the order the phone gives their values; the plan's are `[id, type]`, `integer` or `number`, and a phone given a value that is not a whole number for an `integer` slot, or a count of values other than the plan's slots, stops by name. A piece where a sample does not compile is refused: for example, a negative `width`, which the web drops at parse time and Dragon refuses. So is a value that is not finite, which makes the whole declaration invalid. A phone given such a value stops with the reason. Refused at build time, by name: a slot that changes the box tree, which nodes there are or their write kinds; a number that follows no rule (an `rgb()` alpha); a field or number two slots move; and a slot input exported without `--plan`. The command also lays the page out with the phone's function at every sample and at every set of slots moved together, at the export's viewport and ratio, and refuses the page where that differs from the sample's own compile; the slots moved together are checked at every sample position at once. Known follow-up: the plan records text at the slots' initial values, and the build checks samples' text only at the export's viewport and ratio, so a slot value that changes how a text is shaped at another width or ratio the plan serves is caught on the phone, which stops with `the shape transcript holds no call ...`, not at build. `runMarklessLayout` takes `slots` (each value's bit pattern) and returns, after the boxes, `[node, kind, path, value]` for every bound write number. Checks: `packages/parity/test/markless-slots.test.ts` (`examples/markless-styles/input/slots.native-style-input.json`). At three sets of values no build samples, the phone's function gives exactly what a plan built at those values gives, and the writes and frames of that export. That export passes the Chrome comparison on both targets, and the background and text colours the slots move equal Chrome's computed colours. It also checks the refusals.
- **A style chosen by state between texts with slots.** An element may give `styleByState: [{ when, template }]` instead of `styleTemplate`: one entry per combination of `states`, each a template (text and `{ slot }` holes, or `[]` for empty text). This is how a style that is a template while a condition holds and empty text otherwise reaches Dragon (a menu's `point === null ? '' : \`--x: ${point.x}px\``): Markless gives the condition as a boolean state. Each assignment is compiled with its own text at the sample values, so a slot binds only in the assignments whose text holds it. It may not be combined with a fixed `style`, an `attributesByState.style` or a `styleTemplate`. Checks: `packages/parity/test/markless-style-choice.test.ts` (`examples/markless-styles/input/style-choice.native-style-input.json`). In each case, at values no build samples, the phone's function lays the surface out exactly as a plan built at those values does, and that export passes the Chrome comparison.
- **Fonts.** It compiles with the pinned font map: `sans-serif` is "Dragon Sans", Inter Regular, Bold, Light and Italic from `vendor/fonts/Inter/`. The export's `fonts[].file` is relative to the Dragon checkout, or, with `from: "input"`, to the style input's directory.
- **Author web fonts.** An input's `fonts: [{ url, file }]` names each `@font-face` src url of its `css` that is a file of the app: the url as the CSS spells it, and the file relative to the input file. The command reads each file (the caller owns file access) and adds it to the source snapshot as an asset the url resolves to from the input's sheet, so `@font-face` measures with the file's own tables and the export lists the face by its SHA-256 with `from: "input"`; the reference engine that lays out the export shapes with it as a device app that bundles it does. A url the input names no file for stays `DRAGON_FONT_UNRESOLVED_ASSET`. A WOFF or WOFF2 file is decoded at build time (docs/api.md §2.3): Dragon measures the decoded sfnt, the export lists the face by the SHA-256 of that sfnt with `file: "dragon-decoded-fonts/<sha256-hex>.ttf"` (`.otf` for CFF outlines) and `from: "input"`, and `pnpm run markless:style-export` writes that file at that path relative to the input file, so a host bundles and loads a plain sfnt exactly as for a .ttf and the harness copies it like any other `from: "input"` face (checking its SHA-256 against the id). A .ttf or .otf is listed as its own file. A WOFF2 that does not decode is `DRAGON_FONT_UNREADABLE` (`malformed woff2: <reason>`). The Chrome comparison loads each file as authored at its url, so Chrome decodes the WOFF2 itself. Checks: `packages/parity/test/markless-web-font.test.ts` (Lato as an author font file, .ttf and .woff2, against Chrome on both targets, frames unlike Inter's, a skipped family, the refusals) and `packages/dragon/test/fonts/woff.test.ts` (the decoded tables against the .ttf).
- **A family that is not provided.** In `font-family: 'Nowhere Sans', 'Harbour Lato'` a named family neither declared nor mapped is skipped on every target with the warning `DRAGON_FONT_FAMILY_NOT_PROVIDED` (listed in the export's `warnings`), and text lays out in the next family that resolves, as Chrome does; a list where nothing resolves is still `DRAGON_FONT_UNMAPPED_FAMILY`.
- **Modal dialogs.** It calls `compileNativeStyles` with `topLayer: 'host'`: the Markless hosts present the top layer themselves (they show a `<dialog>` on `showModal()` and take it away on `close()`), so every `<dialog>` is laid out as shown modal and is given `open`. Without `topLayer: 'host'`, `<dialog>` is refused (`DRAGON_UNSUPPORTED_ELEMENT`), as nothing would present it. Details below, under "Modal dialogs and ::backdrop".
- **Support mode.** It calls `compileNativeStyles` with `support: 'lanes'`, as the device lanes compile, because real faces are not yet device-proven in the enforced profiles (see "Limits today"). So every target's `readiness` is `analysis-only`, with the reason. This is the output a device proof runs, not a shipping output.

Checks: `packages/parity/test/markless-style-input.test.ts` exports the attributes rung's real input (`examples/markless-styles/input/attributes.native-style-input.json`). It checks the ids, the cells, the transition table and the `.like.on` background following `state:liked` on both targets, and every refusal above. For the styles and attributes rungs' inputs, this command's frames and writes equal those of the counter tool's Chrome-compared export (`examples/markless-counter/tools/markless-style.ts` on `cw/native-targets`) at 0 device px difference, on both targets and in every assignment.

## Modal dialogs and ::backdrop (`topLayer: 'host'`)

With `topLayer: 'host'` (`InternalOptions.hostTopLayer`), a `<dialog>` is laid out as Chrome lays out one opened with `showModal()` (HTML §4.11.4, css-position-4 §3):

- **Its UA values are Chrome's own**, captured by `pnpm run ua:capture-top-layer` into `packages/dragon/src/ua/chrome-145.<platform>.top-layer.generated.ts` (light and dark): position fixed, zero insets, width and height `fit-content`, auto margins, a solid border, `1em` padding, `calc(100% - 6px - 2em)` maximum sizes, the `Canvas` background and `CanvasText` colour, and `overflow: auto` forced (Chrome's `:modal` rule wins over any author value). The capture fails unless an unstyled element given the declared values reproduces every captured longhand; `packages/parity/test/top-layer-ua.test.ts` checks the committed file against a fresh capture.
- **The top layer.** After resolution (values inherit from the DOM parent, as in Chrome), each dialog leaves its place and becomes one of the root's last children, after its `::backdrop` box, in document order (`analysis/resolve.ts liftTopLayer`). So its containing block is the viewport, nothing around it clips it, and it paints after the page. The export's dialog node has `html` as its parent and its frame against the viewport.
- **`::backdrop`** is a box resolve.ts builds for every dialog (`<dialog id>::backdrop`; Markless ids are kept: `component-edge:0/h2::backdrop`), inheriting from its dialog as the current css-position-4 says, cascading the rules whose selector ends in `::backdrop` matched on the dialog's chain, over Chrome's captured `::backdrop` values (fixed, inset 0, `rgba(0, 0, 0, 0.1)`).
- **The engine** sizes an absolutely positioned box by `min-content`, `max-content` or `fit-content` in either axis (css-sizing-3 §3.2; a height keyword elsewhere is refused by name), and a block `<button>` takes part in its scroll container's scrollable overflow as the block it is (other form controls still refuse their scroll container, FORM-a).
- **Checks:** `packages/parity/test/markless-dialog.test.ts` (a Markless input's dialog, with or without `open`, against Chrome's reference document, which opens every dialog with `showModal()` as the host does; the `::backdrop` box is read from its position, margins, size, padding, borders, `box-sizing` and zoom, untransformed as every frame is, and each Chrome comparison checks that reading against the border box Chrome laid out), `packages/parity/test/top-layer-dialog.test.ts` (the dialog and its contents against Chrome with `showModal()`, at DPR 1 and 3, the backdrop over the viewport in Chrome's computed colour, UA and author), `packages/parity/test/top-layer-layout.test.ts` (the sizing keywords, and scroll containers holding block buttons, against Chrome at DPR 1, 2, 3 and 2.625).

Still refused, by name: a dialog in the export, because a modal dialog is always a scroll container (forced `overflow: auto`), which this entry point emits only with the scroll ranges of the `cw/native-scroll` branch (`a scroll container in a state program is not supported yet (OVFL-B scroll views under SELD-R states)`); the `:modal` pseudo-class (refused as before); `[popover]`, whose `::backdrop` stays refused (the top-layer package); a non-modal `<dialog open>`, which Markless refuses before Dragon sees it.

## What CSS is supported

Support is not restated here. It lives in the support profiles (`packages/dragon/src/profiles/ios.ts`, `android.ts`, generated from the lanes), and `querySupport` answers it per property, value and context. A row is `exact` or `caveat` only when it names a passing comparison against Chrome. The ladder below is the Markless-shaped evidence: each step is a `.tsrx` component in the parity corpus, compared against Chrome 145 by Dragon's own numbers and run on the iOS simulator and Android emulator device lanes.

| Step | Fixture | What it covers |
|---|---|---|
| Box | `ms-box` | padding, margin, border widths, styles and colours per side, corner radii, background colour |
| Text | `ms-text` | font size, weight and colour in Ahem |
| Flex | `ms-flex` | flex row and column, `gap`, `align-items`, `justify-content` |
| Toggle | `ms-toggle` | a class switched by a component state at run time, with rounded corners in both states |
| Press | `ms-press` | `:active` on a pressable element and on its descendant |
| Disabled | `ms-button-disabled`; `examples/markless-styles/input/disabled.native-style-input.json` | `:disabled` and `:enabled` follow the `disabled` attribute's state (`:active` on a button stays refused on native, `packages/parity/test/markless-native-styles.test.ts`); a disabled button reads Chrome's captured `button[disabled]` UA row (`packages/parity/test/markless-disabled.test.ts`: colours and frames against Chrome) |

The checks that prove each step are the parity comparison (`packages/parity/test/parity.test.ts` over the committed Chrome captures) and the device lanes: `device-frames`, `device-applied`, `device-lines` and `device-pixels` for each case, and `device-states` for the toggle's run-time switch. Per-case failures are listed in `packages/parity/out/device-failures-<target>.json`.

## What happens when native cannot do something

Nothing is dropped silently. There are two outcomes, and both name what they refuse.

**A build error.** The compile reports a `Diagnostic` with a code from the catalogue, the target, the source span of the declaration or selector, and a fix. That target is blocked: `targets.ios` is `{ kind: 'blocked', reason: 'the ios compile has errors; see the diagnostics' }` and has no code. Examples the tests pin:

- `:active` before its device proof passes: `DRAGON_UNSUPPORTED_SELECTOR [ios] :active is not supported on ios: no passing device proof of selector:pseudo-class(:active) in interaction/mouse, selector:pseudo-class(:active) in interaction/touch`.
- `:active` on a `<button>`: native hit testing does not go through form controls yet (FORM-a).
- `:active` on a box with `border-radius`: hit testing through rounded corners is not built yet (SELD-R2b).
- A font family list on native, such as `font-family: Helvetica, sans-serif` with both mapped: `DRAGON_UNSUPPORTED_VALUE [ios] font-family: Helvetica , sans-serif is unsupported`. Native text is laid out in Ahem only until the real-font rows are device-proven. A list in which no family is declared or mapped is `DRAGON_FONT_UNMAPPED_FAMILY` on every target, because Dragon never uses a font that happens to be installed; an unmapped named family before one that resolves is skipped with the warning `DRAGON_FONT_FAMILY_NOT_PROVIDED`.
- A `<button>` with no author background or border: Chrome paints it with the platform theme (`appearance: auto`), which waits for the FORM-b package; in normal flow it is also an inline-level control (the RF-INL package), and its UA font (Arial) is not pinned. Give it a background or border, `font-family: inherit`, and a block or flex context. Its disabled look then follows Chrome's `button[disabled]` UA row where the author sets no colour.

**A blocked target with a reason.** The CSS is supported, but the generated state runtime has no writer for it yet, so emitting would lose it. For example, a `box-shadow` inside a state program gives `{ kind: 'blocked', reason: 'app/chip/chip: the state runtime cannot write box-shadow yet' }`. Transitions and animations are also blocked by this entry point for now, with the reason. `@media` bands are emitted (since `cw/native-app-styles`): the state program is the band program of the target's own (assignment, band) cases (`bandStateProgram`), the same one `nativeBandProgram` derives, with one more state `@env#band` whose value is the band index, and `NativeStyleOutput.bands` carries the band table. The export writes it per target as `bands: { atoms, bands, conditions }` (each atom a media feature the host evaluates on the device, each band the truth vector of every atom), and keeps `@env#band` as the state's key. Markless should report a blocked reason as a build error for that platform.

## Limits today

- Interaction states (`:hover`, `:active`, `:focus`) compile on native only inside the parity lanes. A production compile refuses them until the device lanes prove them, and this entry point emits no interaction tables yet.
- Native text is Ahem-only in production (see above).
- One call compiles one component in its own document. Generated names are per component (`Dragon<Name>States`), so two components need two different names.
- The generated Kotlin is in the package `dev.dragon.cases`, which the support files share.
