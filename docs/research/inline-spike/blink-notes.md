# Blink 145.0.7632.6 inline formatting: source reading matched to the probe

The source was read from the GitHub mirror at tag `145.0.7632.6` (`raw.githubusercontent.com/chromium/chromium/145.0.7632.6/third_party/blink/renderer/...`). Every path below is relative to `third_party/blink/renderer/`, and `file:line` refers to that tag. Case ids refer to `probe/*.json` (see README.md). Values are DPR 1 ltr unless stated.

**Notation.**
- **LU** is a LayoutUnit, 1/64 px.
- **A/D** are a box's ascent and descent above and below the baseline.
- **Ahem** at size S has font-unit ascent 0.8·S and descent 0.2·S.

Blink `FontHeight`s are in LU. At device scale N, Chrome lays out at N× (the font and every length are zoomed), so each rounding below happens in device px. Divide by N for CSS px.

## 1. Inline items builder (open/close, `<br>`, U+FFFC)

- **Inline boxes.**
  - An inline box opens with an opaque `kOpenTag` item and closes with a `kCloseTag` item (`core/layout/inline/inline_items_builder.cc:1502-1558` EnterInline, `:1600-1667` ExitInline). Neither adds a character to the text content.
  - A box is an "empty item" when its inline-start (or end) border, padding and margin are all zero (`core/layout/inline/inline_item.cc:32-65`, used at `:119-145`).
  - Cases: f3-box-boundary (`aaa<span>bbb</span>` does not break), f1-empty-root (an empty undecorated span makes no line: container height 0).
- **`<br>`.**
  - A `<br>` is a `LayoutBR`, a LayoutText holding `"\n"` (`core/layout/layout_br.cc:37`).
  - The builder appends it as a `kControl` item with U+000A and text type `kForcedLineBreak` (`inline_items_builder.cc:1139-1175`, the item at `:1157`).
  - Following collapsible spaces are treated as leading spaces and collapse (`:1162-1166`). Case: f2-after-space.
- **Atomic inlines.** An atomic inline is a `kAtomicInline` item holding U+FFFC (`inline_items_builder.cc:1245-1251`).
- **Out-of-flow boxes.** An out-of-flow box is an opaque item with no character (`:1306-1310`). The probe's line-top marker relies on this.

## 2. Line breaker item handling (`core/layout/inline/line_breaker.cc`)

- **Dispatch.** `BreakLine` dispatches per item type (`:974`): open tag `:1032`, close tag `:1036`, control `:1040`, atomic `:1073`.
- **Inline-start and inline-end decorations take inline space.**
  - `HandleOpenTag` adds the open tag's inline-start margin, border and padding to the position (`:3888-3938`, the add at `:3907`).
  - `HandleCloseTag` adds `ComputeInlineEndSize` (`:3946-3947`).
  - Cases:
    - f4-edge-width: `aa bb` plus 15px padding-right is 65 > 60, so `bb` wraps.
    - f4-start-width: 4 + 3 + 6 = 13 px before `bb`.
    - f4-slice: the first fragment has only the start edge (x 23, width 2+5+20 = 27). The second has only the end edge (width 50+5+2 = 57).
- **Box boundaries are transparent to breaking.** A break opportunity before a close tag moves to after the close tag (`:3975-3983`). So a hanging space inside a closing span stays in the span (f3-trailing-space-close, f3-box-space-before-close `aabb ` / `cc`).
- **Atomic inlines always have a break opportunity before and after** outside the sticky-images quirk (`:1127-1150`; the text side is at `:1174-1210`, which checks for an atomic after the text item).
  - f5-break-around: `aaa￼` / `bbb`.
  - f5-break-around-img: `aaaa` / `￼bbb`.
- **Text opportunities** come from `LazyLineBreakIterator` (see §3).
- **Trailing spaces** hang (`HandleTrailingSpaces`, `:2384`).
  - f3-exact-fit: `aaaaa ` fits 50px exactly, and the space hangs.
  - f3-trailing-spaces-close (pre-wrap, rtl): the three hanging spaces extend the span's fragment past the line's left edge (x = -32).
- **Atomic margins** are part of the atomic's inline size (`HandleAtomicInline`, `:2997`, margins at `:3024-3026`). Case: f5-stf-margins (x 10 + margin 7 → border box at 17).

## 3. Break opportunities in text (Ahem-covered ASCII)

- **Fast path.** `LazyLineBreakIterator::ShouldBreakFast` (`platform/text/text_break_iterator.cc:195-240`) uses a pair table for code points up to `kFastLineBreakMaxChar`.
- **The table.** It is generated by `LineBreakData::FillAscii` (`platform/text/character_property_data_generator.cc:433-471`). Later entries override earlier ones:
  - break before `(`, `<`, `[`, `{` after anything, and after `-` and `?` before anything (`:436-441`);
  - then no break before `!`, `)`, `,`, `.`, `/`, `:`, `;`, `?`, `]`, `}` (`:443-456`);
  - then no break after `$`, `'`, `(`, `/`, digits, `<`, `@`, letters, `[`, `^`-`` ` ``, `{` (`:457-469`).
  - `|`, `!`, `%`, `+`, `"` and `;` get no rule that allows a break around them.
- **Hyphen before a digit.** This is hard-coded (`text_break_iterator.cc:204-215`): a break is allowed only if the character before the `-` is ASCII alphanumeric.
- **Measured, in 50px** (f3-*, identical in all 8 environments):

| probe | result | rule |
| --- | --- | --- |
| `aaa-bbb`, `aaa-123`, `123-456` | break after `-` | `:440`; digit case `text_break_iterator.cc:209-213` |
| `aaa?bbb`, `aaa?123` | break after `?` | `:441` |
| `aaa!bbb`, `aaa\|bbb`, `aaa/bbb`, `aaa(bbb`, `aaa)bbb`, `aaa,bbb`, `aaa.bbb`, `aaa;bbb`, `aaa:bbb`, `aaa%bbb`, `aaa$bbb`, `aaa+bbb`, `aaa"bbb`, `aaa{bbb`, `aaa}bbb`, `aaa[bbb`, `aaa]bbb` (and the `123` variants) | no break: one overflowing line | letters/digits → anything is false (`:464`, `:467`, `:461`); `(`, `[`, `{` after a letter are overridden by `:464`/`:467` |
| `a -bbbb`, `a ?bbbb` | `a -` / `bbbb`: break after the punctuation | `:440-441` |
| `a !bbbb` ... `a ]bbbb` (all others) | `a ` / `!bbbb`: break only at the space | space (below U+0021) is outside the table; UAX #14 LB18 |
| `aaa​bbb` (U+200B) | break after U+200B | outside the fast table, so ICU (UAX #14 ZW) |

> **Correction to T044 §1.2.** Chrome does **not** break after `|` (f3-u007c-alpha, f3-u007c-digit). FillAscii has no `|` entry that allows a break, so `'a'..'z' → ALL = false` (`:467`) decides. The "never after `/`" part is confirmed (`:460`).

## 4. Line box height, half-leading and baseline rounding

- **Font A/D.**
  - A font's ascent and descent are rounded to whole device px (`platform/fonts/font_metrics.cc:111-112`, `SkScalarRoundToScalar`).
  - `FixedAscent`/`FixedDescent` convert them to LU with `FromFloatRound` (`platform/fonts/font_metrics.h:130-137`).
  - `line-height: normal` is `FixedLineSpacing` (`font_metrics.h:152-153`; `core/style/computed_style.cc:2572-2575`).
  - A number line-height is stored as a percentage of the computed font size in LU (`computed_style.cc:2579-2580`). A px line-height is `FromFloatRound(px)` (`:2584`).
- **Per box** (`core/layout/inline/inline_box_state.cc:104-164`):
  - `text_metrics = GetFontHeight` (`:125`);
  - `leading = CalculateLeadingSpace(line_height, text_metrics)` (`:149`);
  - `AddLeading` (`:151`, `platform/fonts/font_height.cc:9-13`);
  - `metrics.Unite(text_metrics)` (`:161`).
- **Half-leading floor.** `CalculateLeadingSpace` (`core/layout/inline/line_utils.cc:32-41`) sets:
  - ascent-side leading = `((line_height − (A+D)) / 2).Floor()`, **floored to a whole device px** (LayoutUnit::Floor returns an integer);
  - descent-side leading = the rest.
  - So the descent side gets the odd pixel, and negative leading floors toward −∞.
- **Which boxes contribute (standards mode).**
  - Only inline boxes contribute metrics: the root strut (`inline_box_state.cc:344-352`) and every open tag, even an empty one (`core/layout/inline/logical_line_builder.cc:359-376`, the call at `:372`).
  - Text items contribute nothing, except under the quirks-mode `EnsureTextMetrics` (`:227-239`) or, with `line-height: normal`, their used fonts (`:243-245`).
- **Line height and top.**
  - The line box is `ascent + descent` of the root box's united metrics.
  - Every item is placed relative to the baseline and then moved down by the line ascent (`core/layout/inline/inline_layout_algorithm.cc:597-602`).
  - Lines stack by their own heights (the probe: each line top is the previous top plus its height).
  - An empty line (`IsEmptyLine`) creates no line box (`:555-556`).

Measured matches, worked in LU at DPR 1:

## 5. `<br>` height

- **Rule.** A `<br>` never adds metrics of its own:
  - its `kControl` item is placed with its **parent box's** `text_top` and `text_height` (`logical_line_builder.cc:408-449`, the `AddChild` at `:445`);
  - in standards mode it computes no metrics (`:439-443` is quirks only).
  - Its own `font-size` and `line-height` are ignored.
- **Cases.**
  - f2-big-font and f2-big-font-only: a `<br style="font-size:30px">` leaves the lines at 10.
  - f2-big-lh: a `<br style="line-height:40px">` leaves them at 15.
  - f2-in-big-span: a br-only line inside a 30px span is 30, from the span's box state reopened on that line.
  - The br's rect is zero-width with the parent's text height (f2-*: `br` rects).
- **Trailing `<br>`.**
  - A trailing `<br>` adds no line (f2-trailing).
  - Two trailing `<br>`s add one line (f2-trailing-two).
  - A block holding only a `<br>` has one strut-height line (f2-only).

## 6. vertical-align shifts (`inline_box_state.cc`)

`ApplyBaselineShift` (`:1137`) applies the shifts. Shifts that need the parent's size are queued and applied when the parent closes (`:1150-1206`).

| value | Blink rule | case (span 10px in 20px text, lh 30; inline-block 15x25) | measured |
| --- | --- | --- | --- |
| `sub` | `+(parent.ComputedFontSizeAsFixed()/5 + 1)` (`:1281-1283`) | f5-va-span-sub: 20/5+1 = 5 down | marker 26 vs line baseline 21 |
| `super` | `−(parent font size in LU / 3 + 1)` (`:1284-1286`) | f5-va-span-super: 20/3 → 6.65625 LU, +1 = 7.65625 up | baseline 25.65625, marker 18 |
| length | `−length` (`:1287-1296`) | f5-va-span-5px, f5-va-span-m5px | ±5 |
| percentage | of the element's **own** `ComputedLineHeightAsFixed` (`:1291-1293`) | f5-va-span-50pct: 50% of 30 = 15 up | baseline 33, marker 18 |
| `middle` | `(box A − box D)/2 − round(parent x-height/2)` (`:1297-1304`) | f5-va-span-middle: box A18 D12 → 3 − 8 = −5; f5-va-ib-middle: 25/2 − 8 = 4.5 | ib top 0.5 |
| `text-top` | `child A + parent TextTop` (`:1160-1161`) | f5-va-span-textmtop: 18 − 16 = +2; f5-va-ib-textmtop: 25 − 16 = 9 | ib top 5 |
| `text-bottom` | `parent FixedDescent − child D` (`:1162-1168`) | f5-va-ib-textmbottom: 4 − 0 | ib top 0 |
| `top`/`bottom` | queued on the nearest top/bottom ancestor or the line (`:1308-1321`), applied last against `MetricsForTopAndBottomAlign` (`:1182-1206`, `:1359-1418`) | f5-top-tall: line 60 with the box at the line top; f5-bottom-tall and f5-top-bottom-both: line 60, baseline 55 | as stated |

- **Nested shifts use the parent's computed size.**
  - f5-sub-nested: `smaller` gives 16.6667px, then super gives −(16.65625/3 + 1) = −6.546875. The inner glyph top is 21 − 6.546875 − 11 = 3.453125, as measured.
  - f5-tags-sub-sup uses the UA `sub`/`sup` rules (`core/html/resources/html.css:1355-1363`).
- **`top` and `bottom` metrics** exclude the box's own vertical padding (`:1385-1387`).

## 7. Atomic inline baselines

- **Placement.** An atomic is placed with `LogicalBoxFragment::BaselineMetrics` plus its block-axis margins (`logical_line_builder.cc:470-532`; `core/layout/logical_box_fragment.cc:14-50`). Its margin box is the height it contributes.
- **inline-block.**
  - The block algorithm runs with `BaselineAlgorithmType::kInlineBlock` and marks the fragment "use last baseline" (`core/layout/block_layout_algorithm.cc:1448-1451`).
  - The baseline is the **last** line box's baseline, propagated through block children (`:3622-3647`).
  - Cases:
    - f5-ib-text: last line baseline 15+10 = 25 = line baseline.
    - f5-ib-block-child: the child's last baseline 8 + 8 = 16.
- **No baseline, or a scroll container.**
  - If the inline-block has no baseline, the baseline is synthesized at the **bottom margin edge**. For the alphabetic baseline that is `FontHeight(size, 0)` (`logical_box_fragment.cc:52-62`).
  - A scroll container (`overflow` other than `visible`) forces synthesis (`core/layout/physical_box_fragment.h:167-172`, `block_layout_algorithm.cc:3640-3645`).
  - Cases:
    - f5-ib-empty: height 30 + margin-bottom 4 = 34 = baseline.
    - f5-ib-overflow: 20 + 3 = 23.
- **inline-flex** uses the flex container's **first** baseline (`core/layout/flex/flex_layout_algorithm.cc:80-142` BaselineAccumulator). In order:
  - the first line's major baseline (from baseline-aligned items);
  - its minor baseline;
  - the first item's `FirstBaselineOrSynthesize`.
  - Cases:
    - f5-if-row: the first item's padding-top 7 + 10 = 17.
    - f5-if-column: 8 + 8 = 16.
    - f5-if-align-baseline: major baseline 9 + 8 = 17.
    - f5-if-empty: synthesized from the margin box, 30 + 4 = 34.
- **Shrink-to-fit.**
  - f5-stf-short: width 50.
  - f5-stf-wrap: the width is the available 45, and the lines are 20 wide.
  - f5-stf-min: min-content 30 at available 15.

## 8. Inline box fragments and paint order

- **Fragment geometry.**
  - Each line fragment's border box is the content area (the parent font's A+D) plus vertical padding and border, whatever the line height.
    - f4-vertical-only: rect top −28 = 1 − 20 − 9, height 68.
    - The line stays 12.
  - With `slice`, the inline-start edge is only on the first fragment and the inline-end edge only on the last (f4-slice, f4-nested). `clone` is handled at `inline_box_state.cc:438-441` and `line_breaker.cc:3917-3925`.
  - In rtl, the start edge is on the right (f4-slice rtl: the first fragment extends 7 px to the right of `bb`).
- **Paint order.** Paint walks the lines in order.
  - For each line box, it paints the line's items in fragment-item order (`core/paint/box_fragment_painter.cc:1963-2006` `PaintLineBoxChildItems` → `PaintInlineItems` `:1889-1915`).
  - An inline box fragment paints its background and border first and then its descendants (`core/paint/inline_box_fragment_painter.cc:61-94`: `PaintBackgroundBorderShadow` at `:76` before `PaintObject` at `:92-93`).
  - So a later line's box background covers an earlier line's text.
  - f4-overlap samples:
    - `line1-glyph` (a line-1 glyph pixel) is **red**, span b's line-2 background.
    - `overlap-a-over-b` is red.
    - `line2-glyph` is green.
  - f4-overlap-same: line 2's glyph paints over line 1's bottom border (`line1-bottom-border-on-line2-glyph` is green).
  - The spec's name `NGInlineBoxFragmentPainter` is `InlineBoxFragmentPainter` at this tag.

## 9. `smaller`, `larger` and the monospace medium size

- **`smaller` and `larger`.**
  - `smaller` is `parent / 1.2` and `larger` is `parent × 1.2` (`platform/fonts/font_description.cc:190-196`, called from `core/css/resolver/style_builder_converter.cc:939-944`). This holds for keyword parents too: f6-ahem-medium `small` = 16/1.2 = 13.3333px, not the next table keyword.
  - `small`, `sub` and `sup` are `font-size: smaller` in the UA sheet (`html.css:1347-1349`, `:1355-1363`).
- **Monospace.**
  - `code` is `font-family: monospace` (`html.css:1326-1328`).
  - When exactly the generic `monospace` changes between parent and child (`platform/fonts/font_description.h:243-246`) and the size is not absolute, `CheckForGenericFamilyChange` refetches keyword sizes from the monospace table (`core/css/resolver/font_builder.cc:324-358`). Monospace `medium` is the default fixed size, 13px (`core/css/font_size_functions.cc:91-97`).
- **Measured (f6-*)**, identical under Ahem and monospace parents:

| parent | `small`, `sub`, `sup`, `smaller` | `larger` | `code` |
| --- | --- | --- | --- |
| 10px | 8.33333px | 12px | 10px |
| 16px | 13.3333px | 19.2px | 16px |
| 17.5px | 14.5833px | 21px | 17.5px |
| 23.3px | 19.4167px | 27.96px | 23.3px |

  Under a `medium` parent:
  - Ahem parent: `code` is 13px.
  - monospace parent: the parent itself is 13px and `small` is 10.8333px, while `code` with `font-family: Ahem` returns to 16px.

## Open questions (unexplained by the source; not guessed)

1. **f2-in-span.** After any DOM mutation and relayout, `span.getClientRects()` omits the zero-width rect for the `<br>` piece (`20,2,0,10`), which the first layout reports. The layout of characters and `<br>` is unchanged. The corpus records the first-layout value. The reading above does not show which fragment-item path emits that rect; this matters only if INL1a compares inline-box `getClientRects` around a `<br>`.
2. **Metric halves on macOS.** 17.5px Ahem has descent 3.5 → 3 (f1-fractional), and 20px at DPR 2.625 (52.5 device px) has descent 10.5 → 10 (f1-normal dpr2.625: line 52/2.625 = 19.8095). But `font_metrics.cc:111-112` rounds halves up. This is the existing measured macOS platform rule (docs/decisions.md "What is platform-dependent"; `packages/layout/src/platform-rules.ts`), which is taken to come from CoreText metric values. No new rule is claimed here.
