   - on every BMP code unit 0..0xFFFF, lone surrogates included;

   - on 20,000 seeded mixed strings.
2. `inline.ts`: the anonymous `{ id, ch }` became `LeafChar`, and the anonymous segment type became `Segment`. The `leaves.map(() => [])` and `own.map((p, j) => ...)` callbacks got explicit return types (`Piece[]`, `Placed`).

## Deviations

1. **The missing-fround fault is planted in `percentOf`, not `fromCssPx`.**
   - Dropping the inner fround of `fromCssPx` cannot change any result: `fround(fround(x) * 64) = fround(x * 64)` for every double x. Scaling by a power of two commutes with rounding to float; the overflow boundary lines up at 2^122(1 - 2^-25), and at the subnormal end both truncate to ±0.
   - The planted variant did compile. It changed 0 of 362,516 cases, and a brute-force check found 0 differences in 5,600,238 values: 5M random bit patterns, a sweep of 2^e(1 + m/2000) for e from -160 to 139, and boundary values.
   - A translate test keeps a 460,000-value version of this check.
   - T001's "1,609 failures" for this slip can only have come from a different change.
   - The same inner-fround slip in `percentOf` (`Math.fround(percent)`) fails 780 cases on both targets.
2. **A fourth suite, the library corpus (22,000 cases), in the translated harness.** Swift's `x.rounded()` differs from JS `Math.round` only at negative halves, and the engine only rounds non-negative values (`roundHalfAwayFromZero`). So that planted fault changed 0 vector, units or engine cases. The library suite runs each library operation of the subset on edge inputs through the same translated harness. It catches the fault in 398 cases, and it makes every prelude fault fail whether or not today's engine reaches the helper. Its digest is part of the corpus digest.
3. **The flex order refactor** uses the stable sort directly instead of a named `{ b, i }` type with an index tie-break. The output is identical (stability is guaranteed). With the tie-break, no sort algorithm could differ, and the unstable-sort fault would be invisible in the engine; without it, 83 engine cases catch that fault.
4. **Subset additions the engine needed**, beyond the section 1.2 list:
   - string `+` and `+=` (inline.ts builds run text with `+=`);
   - integer interpolation in templates (`${t.id}:line${j}`), through a `jsNumberToString` helper;
   - `string.toUpperCase()` after `toString(16)`;
   - `new Map([[k, v], ...])` with literal entries (platform.ts);
   - `x++` in expression position (inline.ts `run.chars[i++]`);
   - boolean-literal discriminants (`MeasureResult.ok`);
   - `[...string]` for code points;
   - `for (const [k, v] of map)` (the harness);
   - `interface` with method signatures, translated as a class of closure fields.

   Each is keyed to its TypeScript construct.
5. **Type names.**
   - Union members that are anonymous inside a named alias are named `<Alias>_<discriminant>`, for example `HeightBasis_definite`.
   - Type literals nested in a named type are named by path, for example `PlatformRule_branches`.
   - Unions become protocols (Swift) or sealed interfaces (Kotlin) named `U_<sorted members>`. TypeScript interns SizeValue, MarginValue and InsetValue as one union.
   - Types declared in two files get a file prefix, for example `Flex_Line` and `Inline_Line`. So do names reserved in a target, for example `Inline_Char`.

   Anonymous object types anywhere else are subset violations and were refactored (item 5 above).
6. **Generic functions** are listed in section 1.2 but not implemented. The engine has none, and the checker rejects them ("not supported by the translator yet"), so the checker never accepts code the translator cannot translate.
7. **The harness has a host module** (`harness/host.ts`) with four functions: bit pattern to and from hex, JSON number text to double, and code points to string. It is never translated; each emitter maps the four functions to prelude helpers. The JSON reader, the exact-key decoders (missing and extra keys are rejected) and the writer are subset TypeScript, translated like the engine.
8. **Harness input is one JSON line per case, and output is one line per result.** For engine cases the input is `{"platform","faults","input"}`. The output line holds the measurer key, the LayoutRect list (ids, parents, and x, y, w and h as bits), and `absoluteRects` in Map iteration order. The last part is what exposes an unordered map in the vectors.

## Translator limitations

- Swift output is correct but slower than V8. The engine corpus takes about 12.5 s against about 2.5 s in Node, from allocation (a `JsString` per code point, `JsArray` boxes) and exclusivity checks. The build uses `-O`, never `-Ounchecked`, and exclusivity checking stays on. Kotlin/JVM runs the whole corpus in 5.3 s.
- Kotlin shows 21 "cast is redundant" warnings (explicit casts where Kotlin would smart-cast). Swift builds with 0 warnings.
- `jsNumberToString` is exact for integers below 2^53, which is every use in the engine (line ids). Non-integers are only used in `throw new Error` messages, which are compared only as a threw outcome. They use Swift's shortest digits, but Kotlin/JDK 17's `Double.toString` (not always shortest before JDK 19) could differ from JS in those messages.
- `toString(16)` of a non-integer throws in the helpers rather than printing JS's fractional hex; the engine only formats code points.
- Integer types appear only in helper internals: array index checks (`jsAt`), loop counters over arrays, map slot indices, and integer-to-decimal and hex formatting. Engine values stay `Double`.
- For performance the prelude's canonical-equality fault compares all-ASCII strings by code unit, which is the same as Swift `String` equality for ASCII.
- Each for...of over a string allocates a code-point array.
- For loops whose body contains `continue` use a labelled `do` block (Swift) or `do { } while (false)` (Kotlin), so the incrementor still runs. Loop-local `let` variables are not copied per iteration for closures; the engine never captures a for-loop variable in a closure. The checker does not yet reject that pattern.
- Planted-fault runs whose engine loops for ever are bounded by the 180 s suite limit, not by a per-case watchdog.
- The Swift harness builds as one module, but the engine module is first type-checked alone (`swiftc -typecheck -parse-as-library`). That caught a Foundation-only call in the prelude, which the iOS build then confirmed fixed.
- `.swiftpm/` and `.build/` under the generated Swift package are ignored, and the generated-tree listing skips them.
