## Rulings
### 1_initial_border_width
- **decision:** (c) = (a) plus a recorded Chrome deviation. (b) alone is rejected: a record cannot make the engine distinguish the two cases, so it would become a DPR-specific exception.
- **probe_chrome_145_0_7632_6:** Device px of one top border at DPR 1 / 2 / 3 / 2.625. Initial width, reached by style only, `border: solid`, `border-width: initial`, `unset`, `revert`, or `inherit` from an initial parent: 3 / 3 / 3 / 3 (getComputedStyle gives 3, 1.5, 1, 1.14286px). Authored `medium`: 3 / 6 / 9 / 7. `thin`: 1 / 2 / 3 / 2. `thick`: 5 / 10 / 15 / 13. `3px` and `calc(1px + 2px)`: 3 / 6 / 9 / 7. `inherit` from a parent with style none: 0 at every DPR. `outline-width` and `column-rule-width` initials are also unzoomed (1.5px at DPR 2), while an explicit `medium` is zoomed. Font-size `medium` (16px) is not affected.
- **blink_source:** third_party/blink/renderer/core/css/css_properties.json5 at 145.0.7632.6: border-top-width lines 2626-2650 have default_value "3", type_name int, converter ConvertBorderWidth and affected_by_zoom; outline-width line 4477 is the same. core/css/resolver/style_builder_converter.cc lines 1961-1994: the thin, medium and thick keywords (1, 3, 5) go through CssToLengthConversionData().ZoomedComputedPixels, then floor, with anything in (0, 1) becoming 1. The initial value never passes through the converter, so the stored int 3 is already in zoomed px, which is device px when zoom equals DPR.
- **design:** The compiler keeps provenance. An initial line width (origin 'initial', or a shorthand longhand with LonghandValue.explicit === false) lowers to a new engine input member `{ kind: 'device-px', value }`. It is allowed only in the four borderXWidth fields. value comes from the UA dataset (borderWidthKeywords.medium), never a literal. Authored thin, medium, thick and px widths stay `{ kind: 'px' }`. zoomInput leaves device-px values unmultiplied. At DPR 1 the value equals px, so outputs are identical. validate.ts accepts the new kind only in those four fields. Resolved CssValues, web emission and profile features are unchanged. Native backends (P4) must apply it as device px (3 / scale); record that for P4.
- **deviation_record:** Spec (css-backgrounds-3 border-width: initial medium, computed as an absolute length) against Chrome (initial = 3 device px). At DPR 1 the two readings agree, so the existing registry and its M2 'distinguished at DPR 1' test cannot hold it. Add a separate new registry, packages/layout/src/chrome-deviations-dpr.ts, in the same MF5 shape plus a dpr field on each node. Branches: 'no-width-declared' and 'shorthand-omitted'. Nodes come from the new fixture border-initial-width at DPR 2, 3 and 2.625, plus color-border-sides node long. Controls: authored medium, thin and thick, and the DPR-1 nodes. The planted fault initialLineWidthZoomed (the spec reading) must make every registered node non-exact. chrome-deviations.ts and report.json deviations stay unchanged.
- **latent_finding:** At DPR 1 the resolver copies the parent's `medium` for `border-top-width: inherit` from a parent with style none (compiler gives 3px, Chrome gives 0). It is unreachable today because the m1-s5 profile rejects `inherit` and `initial` on border widths (probed: DRAGON_UNSUPPORTED_VALUE). Do not widen support in P2b. The row needs its own fixture before it is ever supported.

It is added to the milestone-1 corpus and nothing is removed. Reverting R2 or R3 in a /tmp worktree must make at least one node of the fixture non-exact at DPR 1.
- **rebaseline:** The 258 existing top-level vectors, the DPR-1 captures and the emitted CSS stay byte-identical. The only exception is color-border-sides.json (ruling 1): only node long's four border widths change, and its output key stays identical. report.json rows of the 258 existing cases stay identical to base 8228b4e. ### 3_unexplained_1LU
- **decision:** Cause found. Adopt R4.
- **cause:** Blink computes the min-content of a word inside a multi-word text item in HandleTextForFastMinContent (core/layout/inline/line_breaker.cc lines 1356-1362 and 1800-1990). FastMinTextContext::Add (lines 364-376) uses ShapeResult::CachedWidth (platform/fonts/shaping/shape_result.cc lines 2239-2248). That is LayoutUnit(position(end)) minus LayoutUnit(position(start)), and LayoutUnit(float) truncates. The engine uses ceil of the word's own width (textAdvanceAt, fromPxCeil), which is SnappedWidth.
- **probe:** Width LU of a flex item in a width-0 flex row holding 'XXX XX XXXX'. DPR 1: Chrome 11.11px 2844 (engine 2845), 10.02px 2566, 10.3px 2637, 10.06px 2576, 10.39px 2660. DPR 3: 10.3px 7910 (engine 7911), 10.06px 7726 (engine 7727), 10.39px 7979, 11.11px 8530, 10.02px 7696. Single-word 'XXXX' uses ceil in every context tried: min-content, max-content, inline-block and flex (11.11px 2845 at DPR 1; 10.3px 7911 at DPR 3). trunc(pos end) - trunc(pos start) fits all 16 multi-word probes.
- **worker_instruction:** Before coding, read at the tag which path handles a single-word text (inline_node.cc ComputeMinMaxSizes and line_breaker.cc) and write it down. Implement R4 in the subset through the measurer: float glyph positions, per-position truncation. Reproduce every probe value above. The new DPR-1 fixture text-min-content-word-positions.html has both branches.
