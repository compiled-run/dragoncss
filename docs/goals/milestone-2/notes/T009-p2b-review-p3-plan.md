## P3 objective (binding)
P3, the shared lane core for iOS and Android (native-strategy.md 3.1, 3.2, 3.3, 3.5, 3.6 and 3.9 item 13; T007 sequence). Branch t012-p3-lane-core from master after the fast-forward (2beb4a2), in a new /tmp worktree; commit locally only. (1) packages/parity/src/native-dump.ts: the dragon.native-dump/1 TS types, one exported schema description (every field, its type and whether it is required, with integer deviceEdges) and a validator derived from that description. It rejects a missing or extra key at every level, a missing node id, and non-integer deviceEdges. P4 must emit the Swift and Kotlin encoders from this description. (2) packages/parity/src/targets.ts: the ios and android targets. Each has the six lanes (layout-vectors-host, layout-vectors-device, device-frames, device-applied, device-lines, device-pixels). Case lists are derived from the constants: SHARED_DPRS and EXTRA_DPRS from dpr.ts, layoutCases(), corpus-m1-cases.json and the corpus.json and corpus-dpr.json manifests, giving 261 top-level plus 783 DPR vectors = 1044, never a literal. 2.625 is named only through EXTRA_DPRS on android. Tolerances are imported, the sample rules and planted faults are identical, and both targets bind the same nativeLayoutProjection. (3) packages/parity/src/lanes.ts and cli/lanes.ts, with package.json script parity:lanes: it checks lane, case-list, tolerance and sample-rule parity, and it source-scans the lane files for numeric tolerance literals. Lane states are pass, fail, blocked (owner tooling) and not run. blocked is used only when a tool lookup fails; the Android SDK exists, so device lanes are not run until P5. --run-host spawns the existing native:swift and native:kotlin CLIs and parses their counts and digests. layout-vectors-host passes only if every count equals the declared case list and both digests match; with no --run-host it reads the committed out/lanes.json. --require-all fails on any lane that did not pass. --plant <fault> accepts missing-lane, dropped-case, tolerance-literal-2 and unnamed-extra-dpr, and each must exit non-zero with a specific message. Write out/lanes.json deterministically, with no timings. (4) packages/parity/src/samples.ts: a deterministic sample-point generator over snapped geometry, with rules interior, border, outside, radius, clip and edge (T002 notes section 6). (5) packages/parity/src/native-compare.ts, checks (a)-(d): (a) dump frames against the Chrome capture at the same DPR, |delta css px| * dpr <= GATE_DEVICE_PX; (b) applied against expected, exact; (c) pixel samples, channel delta equal to the new GATE_CHANNEL_DELTA = 0 in compare.ts, with edge positions at GATE_DEVICE_PX; (d) frames against snapRect of the TS engine frames, exact. Test (c) against synthetic images; Chrome pixel capture is P6. (6) Reference proof: for every layout case at every DPR of each target (ios at 2 and 3; android at 2, 3 and 2.625), build a dump from the TS engine plus snapRect. It must validate and pass (a) and (d). Negative tests: an edge +2 device px fails (a); an edge +1 device px fails (d) and still passes (a); a changed or missing applied key fails (b); a channel delta of 1 fails (c); a missing node fails; snap disabled on one platform fails. (7) Reports: report.ts and cli/report.ts add only a Native lanes section to report.json, summary.md and index.html, read from out/lanes.json. A lane that is not pass is shown as not met. Every other byte stays identical to 2beb4a2. (8) Android profile: scripts/gen-profile-rows.ts also writes packages/dragon/src/profiles/android.ts. Its rows have exactly the iOS feature@context keys, every status unsupported and proofs []. It is exported from internal.ts, but android is not added to KNOWN_TARGETS or COMMITTED_PROFILES (the public android target is P4). (9) One shared projection: internal.ts gains nativeLayoutProjection(compiled, environment, assignment), and iosLayoutProjection delegates to it. project.ts may only rename the lowered-tree field to a target-neutral name; the digest, diagnostics and KNOWN_TARGETS stay unchanged. A test proves both targets in targets.ts reference the same function, and that iosLayoutProjection output deep-equals nativeLayoutProjection output for every case.
