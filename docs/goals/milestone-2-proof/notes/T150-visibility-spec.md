Master today refuses `visibility` everywhere (`DRAGON_UNSUPPORTED_PROPERTY`; the Tailwind sweep lists `visible`, `invisible`

**Measured for this spec** (Chrome 145.0.7632.6 through Playwright 1.58.2, the repo's pinned build; probes in
/tmp/t074probe):
- **M1. Computed values.** `getComputedStyle().visibility` is `collapse` for `visibility: collapse` on a block and on a flex
  item. A span inside a hidden box computes `hidden` (inherited).
- **M2. Collapse on a flex item keeps its space.**
  - In a row of three 50×20 items, the collapsed middle item stays at x=50, width 50, and the next item at x=100.
  - With `flex: 1` items, the collapsed one keeps 100 px.
  - So Chrome 145 does not implement css-flexbox §4.4 collapsed items; collapse lays out and paints as hidden.
- **M3. Paint.** A hidden box with a red background, a border, `box-shadow: 0 0 0 10px`, an outline and `opacity: .5` paints
  0 red pixels. Its `visibility: visible` child paints [127,127,255] over white, so the hidden parent's opacity group still
  applies to it.
- **M4. Canvas.** `html { visibility: hidden; background: red }` and `body { visibility: hidden; background: red }` still paint
  the canvas red. A visible child of a hidden html paints.
- **M5. Hit testing.**
  - `elementFromPoint` over a hidden box returns what lies beneath it (BODY).
  - Over a visible child of a hidden box it returns the child.
  - Over a collapsed flex item it returns the flex container.
- **M6. Focus.** A hidden `<button>` cannot be focused (`activeElement` is unchanged after `focus()`).

## 1. Scope

**Supported on web, iOS and Android:**
- `visibility: visible | hidden | collapse` on every element Dragon lays out (block, flex containers and items, positioned
  boxes, replaced elements, controls), through the cascade, including inheritance and the CSS-wide keywords.
- Computed values as specified. A descendant may set `visible` again.

**Refused** (located at the declaration and the element; each names the package that lifts it):

| Case | Code | Names | Why |
|---|---|---|---|
| A text view whose runs would differ in visibility: an inline box (display inline, not blockified) whose used visibility differs from its containing block's | `DRAGON_UNSUPPORTED_VALUE` (ios, android) | T150-i (after INL1a and TXT1a) | one Dragon text view draws all runs (decisions.md "Inline layout"); per-run gating is a text-view change |
| `visibility` changed by a state program (SELD-R1a), until T150b | `DRAGON_UNSUPPORTED_VALUE` (ios, android), naming the property | T150b | as PNT2 refuses transform in state programs by name; it needs the device-states lane from SELD-R1b |
| `visibility` in `transition-property` or in `@keyframes` | `DRAGON_UNSUPPORTED_VALUE` | ANIM-b | the "visible while either end is visible" interpolation rule is ANIM's |
| collapse on table parts | — | TBL | Dragon has no tables; `display: table-*` is refused already |

## 2. Rulings

- **R1. Values and computation.** `visibility` is a real longhand: inherited, initial `visible`, computed as specified (M1).
  It joins the captures and emitted CSS under the "New CSS longhands are real longhands" rule. Like PNT1, it has its own
  additive checker, `packages/dragon/test/tools/check-visibility-additive.ts`.
- **R2. Collapse means hidden for every non-table box.**
  - Evidence: M2, and Blink's `IsVisibleToPaint` (`core/paint/box_fragment_painter.cc:83-112`, Chromium BSD). It treats every
    non-visible value alike, except the table row, row-group, column and column-group display types.
  - The engine needs no change: visibility never affects layout here. The s4b "paint never reaches layout" rule applies.
  - TBL owns collapse on table parts when it lands.
- **R3. What hidden suppresses.**
  - A non-visible box paints **none of its own** decorations:
    - outer and inset shadows;
    - background colour and layers (BG2);
    - border;
    - outline;
    - replaced image (REPL-a);
    - control paint (FORM-a);
    - its text glyphs.
  - It **keeps** its stacking context, z-order, opacity group, transform, overflow clip and frame.
  - Descendants paint by their own used visibility (M3; `box_fragment_painter.cc` `PaintObject` gates
    `PaintBoxDecorationBackground` and the mask on `is_visible`; outline and text painters check visibility the same way).
- **R4. The canvas is not affected** (M4). A hidden html or body box gates its own box paint only; the propagated canvas
  background still paints.
- **R5. Native mechanism: gate Dragon's paint, never hide a box view.**
  - `UIView.isHidden` and `View.INVISIBLE` hide the whole subtree and remove it from hit testing and accessibility. That is
    wrong for a hidden box with visible descendants. So:
    1. **`DragonBoxView`** gains `dragonVisible` (default true), set only by the visibility writer.
       - `paintStagesSource` (the EMS registration point that generates `dragonPaintBox`) returns before any stage when it is
         false. That one gate covers every present and future stage (BG2's layers, REPL-a's image, FORM-a's control).
       - `dragonSyncBackground` (`emit/paint/background.ts`) sets the native `backgroundColor` / `ColorDrawable` to nil while
         the box is hidden, and restores it after.
    2. **Companion and phase views** have no CSS children, so they use the platform hidden flag: the shadow companion
       (`DragonShadowView`) and the outline view (`DragonOutlineView`).
    3. **Leaf views** use the platform hidden flag: a text view whose whole text leaf is hidden, and REPL-a's foreign web
       view (WKWebView / android.webkit.WebView). Dragon cannot gate the web view's own paint.
  - Every write goes through one public runtime-callable writer, `dragonVisibility(v, visible)` (RT-1, RT-11). Static values use
    the same writer.
  - Applied readback key: `visibility` (the used value and the gated state), plus `hidden` for each companion and leaf view.
- **R6. Hit testing (T150b).** Blink's rule:
  - `VisibleToHitTestRequest`: `Visibility() == kVisible` and pointer-events not none (`core/layout/layout_object.h:2654-2659`).
    That file has an LGPL header, so it is **class A, reference only**.
  - The same rule is `IsVisibleToHitTest` in BSD `box_fragment_painter.cc:120-157`, and M5 confirms it.
  - `HitFact` gains `visible: boolean`. `rt-hit.ts`'s `visible()` predicate (line 115 on #75) requires both
    `pointerEvents === 'auto'` and `visible`. Text and line nodes take their box's used value.
  - Hidden boxes are skipped, visible descendants are hit, and the search falls through to what lies beneath.
  - Plant `hitIgnoresVisibility` in `HitFaults`.
  - The program facts publish per-node `visibility` for SELD-R2 (focus: M6, a hidden element is not focusable) and P6b
    (accessibility: hidden content is not exposed).
- **R7. States (T150b).** T150b lifts the state-program refusal. It adds `visibility` to the state runtime's typed setters
  through `dragonVisibility`, proven on the device-states lane (SELD-R1b).
- **R8. Web.** The longhand is emitted unchanged. chrome-dual compares the computed strings.

## 3. How it reaches each target

- **Compiler:**
  - the longhand family `css/properties/visibility.ts`;
  - computation and the R1 table refusal in `analysis/paint-values/visibility.ts`;
  - the visibility write and fact in `lower/paint/visibility.ts`;
  - the writer and readback in `emit/paint/visibility.ts`.
  - The used value is resolved per element per reachable state at build time. Nothing on the device parses CSS.
- **iOS:** the gate in `dragonPaintBox`, `backgroundColor` nil, and `isHidden` on companion, outline, text-leaf and web views.
  All writes run with `CATransaction.setDisableActions(true)`, so no implicit fade appears.
- **Android:** the same gate in `dragonPaintBox`, `background = null`, and `View.INVISIBLE` on companion and leaf views
  (INVISIBLE keeps layout and frames; GONE is never used).
- **Web:** the compiled CSS.

## 6. Proof

**Numbers:**
1. chrome-dual computed `visibility` on every fixture, ltr and rtl.
2. Boxes and lines: byte-identical to the same fixture without `visibility`. A committed twin check in
   `check-visibility-additive.ts` proves visibility never moves layout.
3. device-applied: `visibility` and the gate state per box, and the hidden flag per companion and leaf.
4. **T150b:** the device-hit lane's grids equal Chrome's `elementFromPoint` on the visibility fixtures (M5 patterns). The
   device-states lane shows a visibility toggle reaching the state program's own build.

**Pixels:** interior, border, outside and glyph points of hidden boxes compare at delta 0 against Chrome, which shows the
backdrop there. Visible descendants keep their points. The test runs at DPR 2, 3 and 2.625 on the iOS simulator (2, 3) and
the Android emulator (2, 2.625, 3).

**Fixtures (ltr and rtl):**
- `visibility-basic`: hidden, collapse, inherited, visible child of a hidden parent, nested toggles;
- `visibility-paint`: a hidden box with radius, shadow, border, outline and opacity, with a visible child (M3), and a hidden
  stacking context with a visible z-indexed child;
- `visibility-flex`: collapsed and hidden flex items keep their space (M2);
- `visibility-text`: a hidden block's text, and a visible block inside a hidden one;
- `visibility-root`: html or body hidden, the canvas still painted (M4);
- in the train position: `visibility-replaced` and `visibility-control`;
- rejects: `reject-visibility-inline`, `reject-visibility-state` (T150a), `reject-visibility-transition`;
- **T150b:** `hit-visibility-basic`, `hit-visibility-flex` and `state-visibility-toggle`.

**Plants:**
- `visibility-ignored`: the device paints hidden boxes. It must fail device-pixels on both platforms while frames and lines
  pass.
- `visibility-subtree`: the device hides the box view itself, so visible children vanish. It must fail device-pixels.
- **T150b:** `hitIgnoresVisibility`, caught by the host `rt-hit` test and the device-hit lane.

**Support-profile rows:** `visibility: visible | hidden | collapse` on web, ios and android, each naming its fixtures.
Native rows follow P6a's device promotion rule.
